## 1. Контекст ревью

Ревьюировался Architecture Overview v0.2 — версия, в которой были зафиксированы согласованные решения D-02…D-07 и требования A-01…A-08. На момент первоначального ревью предпосылками были:

- Product Vision и Architecture Overview считались достаточной опорой для архитектурных решений;
- пользовательские сценарии в явном виде не описывались;
- решения о запуске, определении корня, Web UI и конкурентной записи рассматривались как согласованные владельцем проекта.

В ходе обсуждения выяснилось, что часть этих решений опиралась на неявные предположения о пользовательском поведении. Появление предложения по пользовательским сценариям меняет оценку: правильным следующим шагом является не правка архитектуры под каждое замечание, а описание сценариев и вывод требований из них.

При этом пауза не отменяет сами замечания. Ниже они разделены на то, что остаётся верным независимо от сценариев, и то, что действительно требует сначала продуктового ответа.

## 2. Исходные замечания R1–R7

### R1. Что именно Web UI может изменять в MVP?

- **Суть:** D-05 и §10.2 исключают редактирование содержимого документов в Web UI, но §4.1, §6.3 и §5.3 описывают формы с несохранёнными правками, сохранение и разрешение конфликтов.
- **Аргументация:** от ответа зависят наличие изменяющих HTTP-запросов, объём CSRF-защиты и сценарии конфликтов. Без ответа автор Web Host Specification не поймёт, что реализовывать.
- **Предложение:** явно перечислить, какие сущности и поля Web UI изменяет в MVP; привести остальные разделы к этому ответу.
- **Оценка с учётом нового контекста:** сам ответ — продуктовое решение, его должны дать сценарии (US-06, US-07). Однако **внутреннее противоречие документа существует независимо от сценариев**: описывать формы и конфликты в UI, объявленном read-only по содержимому, — дефект текста, а не следствие неописанных сценариев. Минимальная правка, не требующая продуктовых ответов: помечать соответствующие разделы как иллюстративные до согласования возможностей UI.
- **Рекомендация:** оставить открытым до US-06/US-07; пометку о предварительности внести при следующем редактировании.

### R2. Строгая optimistic concurrency для внешних писателей

- **Суть:** требование «между проверкой версии и записью не должно оставаться окна для Race Condition» (A-03) невыполнимо относительно внешних писателей (редактор, Git operations, агенты, пишущие напрямую) и требует межпроцессной блокировки.
- **Аргументация:** атомарный rename не является compare-and-swap. Гарантия возможна только при кооперации всех писателей. Требование, помеченное «Согласовано как требование», в такой формулировке нельзя ни выполнить, ни проверить тестом.
- **Предложение:** строгое обнаружение конфликтов для участников, пишущих через RepoDocs; best-effort обнаружение внешних изменений (повторная проверка версии непосредственно перед заменой).
- **Оценка с учётом нового контекста:** аргумент о невозможности остаётся верным независимо от сценариев. От сценариев зависит только **требуемый уровень гарантии** и допустимое поведение при конфликте. Предложенное разделение остаётся рабочей гипотезой, а не принятым решением.
- **Рекомендация:** архитектурное уточнение после сценариев параллельного изменения (US-05, US-08); формулировку A-03 пересмотреть в любом случае.

### R3. Исключения и уточнения алгоритма определения корня

- **Суть:** общий алгоритм (§5.1) не предусматривает исключений для `init` (маркера ещё нет), вызова без аргументов (должен показать справку) и `--root` вне Git; не указано, где `init` создаёт маркер.
- **Аргументация:** по п. 6 алгоритма `repodocs init` в новом репозитории обязан завершиться ошибкой «выполните repodocs init». Это противоречие в самом алгоритме.
- **Предложение:** явно описать исключения для `init` и справки, связь `--root` с Git root и место создания маркера при `init`.
- **Оценка с учётом нового контекста:** противоречия остаются фактом независимо от сценариев. Но форма решения зависит от продуктового вопроса, обязателен ли Git. Если контекст RepoDocs может существовать без Git, алгоритм придётся перестраивать, а не только дополнять исключениями.
- **Рекомендация:** после US-01, US-02, US-03, US-09, US-10; до этого — не дополнять алгоритм вслепую.

### R4. Git как обязательная зависимость каждой команды

- **Суть:** определение корня через `git rev-parse` делает Git CLI обязательным для любой команды. Ограничение v0.1 «специальная интеграция с Git CLI не должна становиться обязательной для базовых операций» удалено без пометки о пересмотре.
- **Аргументация:** Git-native хранение не обязательно означает, что Git — предпосылка каждой операции. Окружения без Git в PATH реальны: минимальные CI-контейнеры, песочницы агентов.
- **Предложение:** либо явно зафиксировать зависимость от Git как осознанное решение, либо определять корень без вызова `git` (поиск `.git` как каталога **или файла**, что покрывает и worktree).
- **Оценка с учётом нового контекста:** вопрос «где Git обязателен» признан продуктовым и стоит отдельного ответа. Замечание о **регрессии относительно v0.1** остаётся верным при любом исходе: удаление ограничения должно быть оформлено как пересмотр, а не произойти незаметно.
- **Рекомендация:** продуктовый ответ после US-01, US-02, US-08; независимо от него — зафиксировать решение явно.

### R5. Фиксированный порт и параллельные запуски

- **Суть:** D-07 (фиксированный порт, ошибка при занятости) не позволяет держать одновременно два Web-хоста, хотя документ сам допускает worktree и несколько проектов.
- **Предложение:** сохранить фиксированный порт по умолчанию, разрешить переопределение (`--port` и/или конфигурация); номер порта отнести к Web Host Specification.
- **Оценка с учётом нового контекста:** это моё предложение, а не решение; D-07 остаётся согласованным. Необходимость нескольких одновременно работающих хостов действительно должна следовать из сценариев (US-05, US-10), а не из предположений.
- **Рекомендация:** вернуться после соответствующих сценариев; при подтверждении потребности — Web Host Specification.

### R6. Получение токена браузером при `--no-open`

- **Суть:** §5.3 требует авторизации по токену и исключения утечки токенов в URL, но не описывает, как браузер получает токен, особенно при `--no-open`.
- **Предложение:** одноразовый токен в URL с немедленным обменом на cookie (`HttpOnly`, `SameSite=Strict`), URL печатается в терминал при `--no-open`.
- **Оценка с учётом нового контекста:** требования безопасности остаются в силе; конкретный механизм — техническое решение для Web Host Specification, а не продуктовый вопрос. Но сценарий запуска UI без автоподкрытия браузера должен быть описан и на пользовательском уровне: что видит и делает пользователь при `--no-open`.
- **Рекомендация:** оставить открытым до Web Host Specification.

### R7. Редакционная ошибка в §11.3

- **Суть:** список открытых вопросов Web UI завершается точкой с запятой, следующий пункт, вероятно, потерян.
- **Оценка с учётом нового контекста:** не связана с продуктом; восстановить потерянный пункт нужно при следующем редактировании.
- **Рекомендация:** можно исправить независимо от сценариев.

## 3. Дополнительные наблюдения

Не претендуют на полноту, перечислены только то, что следует из документов.

### 3.1. Статусы «Согласовано» против паузы

В §12 решения и требования помечены «Согласовано». Часть из них (A-03, A-08, D-05 в части границ UI) теперь признана зависящей от неописанных сценариев. Пока статусы не изменены, следующий читатель — человек или агент — примет их за окончательные.

**Предложение:** добавить в §12 пометку о том, что статусы отражают состояние до появления User Scenarios; решения, зависящие от сценариев, считаются предварительными. Это редакционная правка, не пересмотр решений.

### 3.2. Терминология

«Проект», «корень проекта», «Git root», «каталог с `.repodocs/`» местами используются почти как синонимы. Сценарии должны показать, совпадают ли эти границы; до этого в Architecture Overview стоит развести определения.

### 3.3. Матрица возможностей интерфейсов

Единый Application Services задаёт общую бизнес-логику, но не отвечает на вопрос, какие use cases доступны через CLI, а какие через Web UI. После сценариев это удобно свести в короткую матрицу; она же снимет R1 и часть вопросов §11.2.

### 3.4. Ценность продукта

В ревью Product Vision остаётся открытым вопрос, чем RepoDocs отличается от «папки с Markdown-файлами и `CLAUDE.md`». Сценарии — подходящее место, чтобы показать эту разницу на пользовательских потоках (валидация, связи, единый контекст для агентов), а не только на списке возможностей.

### 3.5. Объём слоя требований

Предложенная цепочка добавляет Requirements Specification между сценариями и архитектурой. Для продукта, чей принцип — лёгковесность, это риск роста документации. Предложение само оговаривает, что отдельный документ не нужен ради формы; поддерживаю: если требования компактно выводятся из сценариев, их можно зафиксировать в сценариях или коротком разделе.

### 3.6. Процессное замечание

Ветка PR #4 была создана от старого `main`: в diff она удаляла `AGENTS.md` и заменяла `CLAUDE.md` устаревшей версией. Перед добавлением этих заметок актуальный `main` влит в ветку. Стоит закрепить ожидание: ветка PR должна быть в актуальном состоянии относительно `main` до начала ревью — иначе ревью проходит по устаревшей базе.

## 5. Рекомендации по дальнейшему ревью

1. **Сразу, без ожидания сценариев:** исправить R7, добавить пометку о предварительности статусов (3.1), развести терминологию (3.2). Это не меняет решений.
2. **Сценарии в первую очередь:** US-01–US-03 (создание, подключение, инициализация), затем US-05 — сценарий передачи контекста агенту, ради которого продукт существует. Далее US-06/US-07 для границ UI, US-08/US-10 для Git и worktree, затем US-04 и US-09.
3. **После сценариев:** ответить на вопрос «обязателен ли Git», затем пересмотреть R3 и R4; собрать матрицу возможностей интерфейсов и закрыть R1; уточнить требования конкурентной записи и пересмотреть A-03 (R2); проверить необходимость нескольких Web-хостов (R5).
4. **После этого:** вернуться к Architecture Overview v0.2 и внести правки; механизмы авторизации и порта — в Web Host Specification (R6, R5).
5. **Закрытие веток ревью** — после проверки правок, по процессу из `AGENTS.md`; ведущий PR — владелец проекта.
