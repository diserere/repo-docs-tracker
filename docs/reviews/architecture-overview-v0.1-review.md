## 1. Общая оценка

Разбиение на слои верное. CLI правильно включён в MVP как основной интерфейс для агентов, а MCP вынесен на следующий этап. Принципы «file-based source of truth» и «derived data is disposable», а также отказ от SQLite как первичного хранилища согласуются с Product Vision.

Документ закрывает одно из замечаний к Product Vision: форма продукта теперь определена — локальное Web-приложение плюс CLI.

Главные проблемы:

- ответственность Repository Adapter перегружена (A1–A3);
- не учтены два требования, которые прямо вытекают из принципа Git-native (A4, A5).

## 2. Решения владельца продукта

1. **Единый прикладной слой.** Web UI, CLI и будущий MCP работают через одни и те же Application Services. Подтверждено и уже отражено в разделе 3.3.
2. **Запуск — CLI-first.**
   - `repodocs` без аргументов показывает краткий статус проекта и справку. Сервер не запускает, браузер не открывает.
   - `repodocs serve` (название обсуждаемо) поднимает локальный сервер и открывает браузер. Флаг `--no-open` отключает открытие браузера.
   - Как команда определяет корень проекта — см. замечание A8.
3. **CLI полностью неинтерактивный.** Все параметры создания и изменения передаются флагами, интерактивных вопросов нет. Сценарий для человека: создать через CLI костяк сущности с минимумом полей, а дополнить её в Web UI.
4. **Редактирование в Web UI.**
   - Preview Markdown обязателен уже в MVP.
   - WYSIWYG-редактор не нужен, вероятно, и в дальнейшем.
   - Действие «открыть во внешнем редакторе» (системный редактор или IDE) очень желательно.

## 3. Замечания ревьюера

### A1. Repository Adapter совмещает несколько разных ответственностей

**Важность:** важное · **Раздел:** 3.4

Сейчас у Repository Adapter четыре разные обязанности:

| Ответственность | Комментарий |
| --- | --- |
| Чтение/запись, атомарная запись, безопасность путей | Собственно хранилище, здесь всё на месте |
| Преобразование файлов в доменные модели и обратно | Отдельная задача (codec/serializer). Формат хранения — открытый вопрос № 1, поэтому его стоит изолировать |
| Отслеживание внешних изменений файлов | Это не хранилище, а источник событий. Нужен только долгоживущему Web-хосту. CLI выполняет одну команду и завершается, watcher ему не нужен |
| Точка расширения для Workspace | Неверная граница (см. A2) |

**Предложение:**

- Различать **порт** и **реализацию**. Application Services зависят от интерфейса хранилища проекта (условно `ProjectStore`), а файловая реализация — один из адаптеров. Структура `adapters/repository-fs` в разделе 7 это уже подразумевает, но в тексте раздела 3.4 этого нет.
- Выделить **codec** (Markdown + YAML front matter ↔ доменная модель) в отдельный компонент, который использует файловая реализация хранилища.
- Выделить **watcher** в отдельный компонент Web-хоста. Он публикует события об изменениях, Application Services инвалидирует кэш, UI обновляется.
- **Переименовать** компонент. Слово «Repository» здесь одновременно означает Git-репозиторий и паттерн Repository, а в документации RepoDocs слово «репозиторий» встречается постоянно. Варианты: `Project Store`, `Storage Adapter`.

### A2. Workspace должен работать поверх Application Services, а не поверх хранилища

**Важность:** важное · **Разделы:** 3.4, 9

Сейчас предлагается, чтобы Workspace обращался к проектам через Repository Adapter. Тогда Workspace получит прямой доступ к данным в обход Domain Core и правил валидации. Это противоречит принципу «Core before interfaces» и требованию раздела 3.7 не обходить Core.

**Предложение:** ввести понятие «контекст проекта» — набор Application Services и хранилища, привязанный к одному корню. Workspace держит несколько таких контекстов и агрегирует результаты их сервисов. В MVP контекст ровно один.

### A3. Версия сущности как часть контракта хранилища

**Важность:** уточнение · **Разделы:** 3.4, 6

Optimistic concurrency из раздела 6 невозможна без поддержки на уровне хранилища.

**Предложение:** при чтении хранилище возвращает вместе с сущностью **токен версии** (например, хэш содержимого файла). При записи принимает ожидаемую версию и отклоняет запись, если файл с тех пор изменился. Это стоит зафиксировать в архитектуре как обязанность хранилища.

### A4. Сохранение форматирования при перезаписи файлов (round-trip)

**Важность:** важное, сейчас отсутствует · **Разделы:** 3.4, 6 (новое требование)

Файлы редактируют и люди, и агенты, и RepoDocs. Если RepoDocs при каждой записи сериализует сущность заново, то меняется порядок ключей YAML, пропадают комментарии и неизвестные поля, переформатируется тело Markdown. Тогда изменение одного статуса задачи даёт diff на весь файл. Это прямо нарушает Git-native: diff перестаёт отражать смысл изменения, а merge-конфликты возникают на пустом месте.

**Предложение:** добавить архитектурное требование. При изменении сущности RepoDocs меняет только затронутые поля и сохраняет:

- порядок и форматирование остальных ключей front matter;
- комментарии YAML;
- поля, неизвестные текущей схеме;
- тело документа, если оно не редактировалось.

Это влияет на выбор YAML-библиотеки и на устройство codec (A1). WYSIWYG-редактор несовместим с этим требованием, что согласуется с решением владельца продукта (раздел 2, п. 4).

### A5. Идентификаторы, безопасные при работе с ветками

**Важность:** важное, сейчас отсутствует · **Разделы:** 3.1, 3.6

В примерах CLI используются последовательные идентификаторы (`TASK-0001`). Если в двух Git-ветках независимо создать по новой задаче, обе получат одинаковый следующий номер. После merge проверка уникальности идентификаторов (раздел 3.1) упадёт, и разрешать конфликт придётся вручную, с переименованием ссылок.

Работа в ветках — базовый сценарий Git-native продукта, причём даже для одного разработчика: параллельные ветки, работа агентов в отдельных worktree.

**Предложение:** зафиксировать в архитектуре требование, что идентификаторы сущностей уникальны без координации между ветками. Конкретную схему выбрать в Data Model & Storage Specification. Варианты:

- короткие случайные идентификаторы или ULID;
- стабильный уникальный ID плюс человекочитаемый номер-алиас, который пересчитывается или проверяется командой `validate`.

### A6. CLI вызывает Application Services в своём процессе

**Важность:** уточнение · **Разделы:** 3.6, 4.2

Из документа не ясно, обращается ли CLI к запущенному Web-хосту по HTTP или вызывает Application Services напрямую.

**Предложение:** явно зафиксировать, что CLI вызывает Application Services **внутри собственного процесса** и не требует запущенного сервера. Агенту не нужно поднимать сервер, чтобы прочитать задачу. Одновременная работа CLI и открытого Web UI корректна за счёт уже описанных механизмов: watcher в Web-хосте (A1) и проверки версии при записи (A3).

### A7. Безопасность локального HTTP-сервера

**Важность:** важное · **Раздел:** 5

Ограничение «слушать только loopback» не защищает от двух угроз:

- вредоносной веб-страницы в браузере пользователя, которая шлёт запросы на `localhost` (CSRF);
- атак через DNS rebinding.

Для сервера, который умеет изменять файлы, это реальный риск.

**Предложение:** добавить в требования раздела 5:

- проверку заголовка `Host` (и `Origin` для изменяющих запросов);
- одноразовый токен доступа, генерируемый при запуске `serve` и передаваемый в URL, который открывается в браузере (аналогично Jupyter).

### A8. Определение корня проекта

**Важность:** важное · **Разделы:** 2.2, 5, 3.6

Раздел 5 требует, чтобы приложение получало корневой путь проекта явно, но не говорит, как именно. Это важно: от корня зависит граница всех операций чтения и записи.

Варианты:

1. **Всегда указывать корень флагом** (`repodocs --root <путь> ...`). Надёжно, но неудобно. Агенты будут регулярно ошибаться в путях.
2. **Считать корнем текущую директорию.** Команда, запущенная из подкаталога (например, `src/`), не найдёт проект.
3. **Искать корень вверх от текущей директории**, как это делает Git с каталогом `.git`.

**Предложение:** вариант 3 со следующими правилами.

- `repodocs init` создаёт в корне проекта каталог-маркер (условно `.repodocs/`) с конфигурацией RepoDocs.
- Любая команда поднимается от текущей директории вверх и ищет маркер. Первый найденный каталог с маркером — корень проекта.
- Поиск не поднимается выше корня Git-репозитория. Корень Git — **предел поиска, а не запасной вариант**: без маркера корень Git проектом RepoDocs не считается. Это исключает случайный захват чужого `.repodocs/` в родительских каталогах (например, в `~/Projects` или в домашнем каталоге).
- Маркер не найден — ошибка с подсказкой выполнить `repodocs init`.
- Явно указанный корень (флаг `--root`) имеет приоритет над поиском.
- Найденный корень всегда виден пользователю: например, `repodocs` без аргументов показывает его в статусе проекта.

Следствия:

- **Граница безопасности.** Найденный корень — та самая граница из раздела 5, поэтому поиск должен быть детерминированным и прозрачным.
- **Агенты.** Команды работают из любого подкаталога проекта без дополнительных флагов.
- **Git worktree.** У каждого worktree свой корень. Агенты в параллельных worktree работают со своими копиями данных, что согласуется с A5. Техническая деталь: в worktree `.git` — файл, а не каталог.
- **Вложенные проекты.** Если в монорепозитории несколько маркеров, выбирается ближайший к текущей директории.
- **`repodocs serve`** определяет корень один раз при запуске и работает с ним до остановки.
- **Принцип «Explicit over implicit»** (раздел 2.2) не нарушается. Он запрещает сканировать диск в поисках проектов, а текущая директория — явный выбор пользователя.

## 4. Ответы на открытые вопросы (раздел 11)

1. **Формат хранения.** Markdown + YAML front matter для всех сущностей (документы, задачи, решения). **Один файл на сущность**, без общих файлов вроде единого `backlog.md`: так меньше merge-конфликтов и diff понятнее. Структурированные данные хранятся только во front matter, тело — свободный Markdown. Конфигурация проекта — в YAML.
2. **Организация приложения.** Для MVP — один npm-пакет с одним исполняемым файлом `repodocs`. Собранный Web UI поставляется внутри пакета, Web-хост и CLI — режимы одного приложения. Монорепозиторий с отдельными пакетами для MVP избыточен. Границы модулей держатся структурой каталогов и правилами линтера на импорты.
3. **Редактирование.** См. решение владельца продукта (раздел 2, п. 4). Технически достаточно редактора исходного текста (например, CodeMirror) с preview и действия «открыть во внешнем редакторе».
4. **Вывод CLI.**
   - По умолчанию человекочитаемый вывод, у всех команд чтения есть флаг `--json` со стабильной документированной схемой.
   - Команды создания и изменения неинтерактивные (см. раздел 2, п. 3). Ошибки валидации возвращаются с ненулевым кодом выхода и понятным сообщением.
   - Первоочередные команды: `init`, `task list/show/create/update`, `doc list/show`, `validate`.
   - **`repodocs validate`** проверяет схему, уникальность идентификаторов и ссылочную целостность, при ошибках выходит с ненулевым кодом. Его можно запускать в pre-commit hook и CI. Это одно из самых сильных отличий RepoDocs от «просто папки с Markdown-файлами»: ту папку никто не валидирует.
5. **Внешние изменения в UI.**
   - Если в открытой форме нет несохранённых правок, она молча перезагружается.
   - Если правки есть и при сохранении обнаружено расхождение версий (A3), UI показывает diff и три варианта: перезаписать, загрузить новую версию, скопировать свой текст.
6. **Запуск приложения.** См. решение владельца продукта (раздел 2, п. 2).
