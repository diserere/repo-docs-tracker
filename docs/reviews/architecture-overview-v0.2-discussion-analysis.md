## 1. Общий вывод

В ходе обсуждения семи замечаний Claude Code стало ясно, что часть проблем Architecture Overview v0.2 связана не только с точностью архитектурного текста. Не хватает промежуточного продуктового слоя — согласованных пользовательских сценариев и рабочих потоков.

Мы начали обсуждать конкретные механизмы (определение корня, зависимость от Git CLI, редактирование через Web UI, конкурентную запись, параллельные запуски) раньше, чем достаточно подробно описали, как пользователь начинает работу, подключает проект, взаимодействует с RepoDocs и возвращается к нему.

Поэтому сейчас не следует механически исправлять v0.2 по каждому замечанию. Сначала нужно подготовить User Scenarios & Core Workflows и вывести из них требования. Затем повторно оценить архитектурные положения. Замечания Claude остаются полезными: они показывают неоднозначности и места, где документ нуждается в проверке.

## 2. Разбор замечаний R1–R7

### R1. Что именно Web UI может изменять в MVP?

**Замечание:** документ исключает редактирование содержимого Markdown-документов, но в других местах описывает создание/изменение сущностей, несохранённые правки и изменяющие HTTP-запросы. Неясно, допускается ли изменение метаданных задач и других структурированных полей.

**Наше обсуждение:** прежнее ограничение касалось содержимого документов, а не обязательно всех операций изменения. Из него нельзя вывести ни полностью read-only UI, ни наличие конкретных форм редактирования.

**Вывод:** замечание обоснованно. Сначала описать сценарии работы с документами и задачами, затем определить доступные операции Web UI и CLI. До этого не менять D-05 и связанные разделы. **Статус:** требует продуктового уточнения; особенно US-06 и US-07.

### R2. Строгая optimistic concurrency для внешних писателей

**Замечание:** строгая гарантия отсутствия race condition для обычных файлов не может быть обеспечена относительно всех внешних процессов без их кооперации. Проверка хэша с последующей заменой не является атомарным compare-and-swap. Межпроцессные блокировки добавляют сложность.

**Наше обсуждение:** A-03 был сформулирован слишком категорично. Нужно различать процессы RepoDocs (CLI и Web-хост) и внешних писателей (редакторы, Git operations, сторонние агенты). Для процессов RepoDocs можно проектировать общую синхронизацию; внешние изменения могут требовать best-effort обнаружения.

**Вывод:** предложение Claude о строгом контроле для участников RepoDocs и best-effort обнаружении внешних изменений выглядит разумной гипотезой, но не принято. Сначала выяснить по сценариям, какие гарантии реально нужны. **Статус:** A-03 подлежит пересмотру; новая модель не утверждена.

### R3. Исключения и уточнения алгоритма определения корня

**Замечание:** общий алгоритм конфликтует с init (маркера ещё нет), вызовом repodocs без аргументов (должен показать справку), а также оставляет неясным поведение --root вне Git и место создания маркера.

**Наше обсуждение:** A-08 ранее подробно задавал Git root как предел поиска и .repodocs/ как маркер. Затем возник более базовый вопрос: обязателен ли Git для создания и использования проектного контекста.

**Вывод:** замечание выявляет реальные противоречия, но окончательный алгоритм зависит от сценариев создания, подключения и повторного открытия проекта, а также работы без Git и в worktree. Определение корня — следствие продуктовой модели, а не её исходная предпосылка. **Статус:** A-08 требуется пересмотреть после US-01, US-02, US-03, US-09 и US-10.

### R4. Git как обязательная зависимость каждой команды

**Замечание:** использование git rev-parse делает Git CLI обязательным даже для базовых команд. Это расходится с формулировкой v0.1 о необязательности специальной интеграции с Git CLI для базовых операций.

**Наше обсуждение:** Git-native хранение не обязательно означает, что Git должен быть предварительным условием каждой операции. Проектный контекст потенциально может существовать до инициализации Git.

**Вывод:** разделить Git как механизм версионирования, Git CLI как runtime-зависимость команд и возможность работы с локальным контекстом без Git. Нельзя объявлять Git CLI обязательным или необязательным повсеместно до описания сценариев. **Статус:** открытый продуктовый вопрос; связан с US-01, US-02 и US-08.

### R5. Фиксированный порт и параллельные запуски

**Замечание:** фиксированный порт по умолчанию мешает параллельной работе с несколькими проектами или worktree. Claude предложил сохранить фиксированное значение по умолчанию, но разрешить явное переопределение через --port или конфигурацию.

**Наше обсуждение:** D-07 (фиксированный порт, ошибка при занятости) ранее согласовано. Явное переопределение не согласовано.

**Вывод:** проверить, действительно ли пользовательские сценарии требуют нескольких одновременно работающих Web-хостов. --port — возможное расширение, не принятое решение. **Статус:** D-07 сохраняет прежний статус; переопределение порта открыто. Вернуться после US-05 и US-10.

### R6. Получение токена браузером при --no-open

**Замечание:** не описано, как браузер получает токен авторизации, особенно когда repodocs serve --no-open не открывает браузер. Claude предложил одноразовый токен в URL с обменом на cookie и вывод URL в терминал.

**Наше обсуждение:** требование локальной авторизации, защиты от CSRF и безопасной передачи токена остаётся актуальным. Конкретная схема не утверждалась.

**Вывод:** предложение Claude — один из возможных технических механизмов, не принятое решение. Пользовательский сценарий должен обеспечивать понятный запуск UI как с автоматическим открытием браузера, так и без него. Детали остаются для Web Host Specification. **Статус:** требования безопасности сохраняются; механизм авторизации открыт.

### R7. Редакционная ошибка в §11.3

**Замечание:** последний пункт списка заканчивается точкой с запятой, после чего начинается следующий раздел.

**Вывод:** независимая редакционная правка. Её можно выполнить при следующем редактировании Architecture Overview, но она не требует возобновлять архитектурную работу прямо сейчас. **Статус:** отложенная редакционная правка.

## 3. Дополнительные предпосылки для перепроверки

1. **«Один явно определённый Git-проект» в границах MVP.** Возможно, формулировка слишком узкая, если контекст RepoDocs может существовать без Git.
2. **Термины «проект», «корень проекта», «Git root» и директория с .repodocs/.** Сейчас они местами используются почти как синонимы. Сценарии должны показать, совпадают ли эти границы.
3. **File Watcher и внешние изменения.** Нужно определить, какие сценарии требуют обновления UI и какие гарантии обнаружения изменений ожидаются.
4. **Матрица возможностей интерфейсов.** Единый Application Services не определяет, какие use cases доступны через Web UI и CLI. Это нужно вывести из сценариев.
5. **Параллельная работа с worktree.** Требования к уникальным ID уже учитывают ветки/worktree, но влияние этого сценария на запуск Web UI и порты не было согласовано.

## 4. Принципы, которые пока выглядят устойчивыми

Пауза ревью не означает, что всё нужно начинать заново. В текущем контексте полезными остаются следующие архитектурные направления:

- единый Application Services для CLI и Web UI;
- самостоятельный запуск CLI без Web-хоста;
- локальное файловое хранение как основной источник истины;
- сохранение неизвестных полей и незатронутого форматирования;
- уникальные ID без координации между Git-ветками;
- автономность проектов и отсутствие зависимости проекта от будущего Workspace;
- loopback-only Web-хост в MVP и защита браузерных запросов;
- отсутствие собственного AI runtime в MVP.

Это оценка устойчивости принципов, а не повторное формальное утверждение всех решений. Если сценарии выявят противоречия, их также следует пересмотреть.
