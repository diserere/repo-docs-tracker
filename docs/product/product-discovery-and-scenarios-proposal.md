# RepoDocs — необходимость продуктовых сценариев и план дальнейшей проработки

**Статус:** предложение по результатам обсуждения Architecture Overview v0.2  
**Автор:** ChatGPT  
**Версия:** 0.1  
**Дата:** 2026-11-06  
**Связанный PR:** [#4 — Architecture Overview v0.2](https://github.com/diserere/repo-docs-tracker/pull/4)

> Документ фиксирует обнаруженный пробел в процессе проектирования RepoDocs и предлагает следующий этап продуктовой проработки. Это не утверждённая спецификация требований и не изменение действующих архитектурных решений.

## 1. Контекст

В ходе обсуждения и ревью Architecture Overview v0.2 обнаружилось, что между Product Vision и Architecture Overview не хватает отдельного слоя, описывающего пользовательский опыт на уровне основных сценариев.

Product Vision отвечает прежде всего на вопросы:

- для кого создаётся RepoDocs;
- какую проблему продукт решает;
- какие принципы и ограничения определяют его позиционирование.

Architecture Overview отвечает на другой вопрос: из каких частей состоит система и как эти части взаимодействуют.

Но до фиксации архитектуры необходимо достаточно ясно понимать, **как пользователь начинает работу с RepoDocs, какие действия совершает, каких результатов ожидает и в каких условиях использует продукт**.

Сейчас этот слой явно не оформлен. В результате некоторые архитектурные решения обсуждались без надёжной опоры на пользовательские потоки. Это создаёт риск преждевременной фиксации технических ограничений, которые могут не соответствовать реальным сценариям.

## 2. Наблюдаемая проблема

В Architecture Overview v0.2 уже присутствуют решения и требования, затрагивающие пользовательское поведение, хотя сами сценарии ещё не описаны в достаточной степени.

Примеры:

- **Определение корня проекта (A-08).** Алгоритм поиска Git root и маркера `.repodocs/` был сформулирован до того, как мы описали, как пользователь создаёт новый проект, подключает существующий или повторно открывает проект.
- **Обязательность Git.** Из того, что RepoDocs Git-native и хранит данные в проектном репозитории, ещё не следует автоматически, что Git должен быть обязательной предпосылкой для каждого сценария запуска и каждой команды.
- **Редактирование в Web UI (R1).** Чтобы определить, какие изменяющие операции доступны в UI, сначала нужно описать, какие пользовательские задачи он должен решать. Исключение редактирования Markdown-документов само по себе не отвечает на вопрос о редактировании структурированных полей задач и других сущностей.
- **Конкурентная запись (A-03 / R2).** Требуемая строгость гарантий зависит от того, какие участники и процессы реально должны одновременно изменять данные: экземпляры RepoDocs, редакторы, Git operations, агенты, работающие напрямую с файлами.
- **Параллельная работа с проектами и worktree (R5).** Требования к запуску нескольких экземпляров Web UI и выбору порта должны выводиться из сценариев, а не только из предположений о будущей эксплуатации.
- **Первичная инициализация.** Алгоритм определения корня должен учитывать особые сценарии `init`, справки и явного указания пути, а не рассматриваться как единый предварительный шаг для всех команд.

Это не означает, что перечисленные архитектурные решения неверны. Это означает, что часть из них пока недостаточно обоснована пользовательскими сценариями.

## 3. Предлагаемый промежуточный артефакт

Предлагается подготовить документ **User Scenarios & Core Workflows** — описание основных пользовательских сценариев и рабочих потоков RepoDocs.

Его задача — зафиксировать ожидаемое поведение продукта на уровне взаимодействия пользователя и AI-агента с системой, не предрешая технические механизмы реализации.

Сценарий должен описывать:

1. **Акторов:** пользователь, AI-агент или оба.
2. **Предусловия:** состояние проекта и необходимые исходные условия.
3. **Триггер:** что побуждает начать сценарий.
4. **Основной поток:** последовательность действий и ожидаемых реакций системы.
5. **Альтернативные потоки и исключения:** другие допустимые варианты и ошибки.
6. **Результат:** какое состояние или ценность получает пользователь.
7. **Участие интерфейсов и инструментов:** CLI, Web UI, Git и другие средства — только на уровне пользовательского взаимодействия.
8. **Открытые вопросы:** то, что требует отдельного продуктового решения.

При описании важно различать:

- **ожидаемое поведение** — что пользователь может или должен получить;
- **ограничение продукта** — что продукт намеренно не делает;
- **предположение** — гипотеза, которую нужно проверить;
- **технический механизм** — возможный способ реализации, который не следует преждевременно фиксировать в сценарии.

## 4. Черновой перечень сценариев

Ниже приведён стартовый список для обсуждения. Он не является утверждённым или исчерпывающим.

| ID | Сценарий | Основной вопрос |
| --- | --- | --- |
| US-01 | Создание нового проекта | Как пользователь начинает работу в пустой директории? |
| US-02 | Подключение существующего проекта | Как RepoDocs подключается к уже существующей проектной директории? |
| US-03 | Первичная инициализация RepoDocs | Когда и каким действием создаётся структура RepoDocs? |
| US-04 | Первичное наполнение контекстом | Как пользователь создаёт или импортирует первые документы, решения и задачи? |
| US-05 | Повседневная работа пользователя и AI-агента | Как они получают контекст и вносят изменения? |
| US-06 | Работа с документацией | Как пользователь находит, читает, создаёт и изменяет документы? |
| US-07 | Работа с задачами | Как пользователь создаёт, просматривает, изменяет и связывает задачи? |
| US-08 | Работа с Git | Как проектный контекст ведёт себя при commit, branch, merge и checkout? |

Перечень следует уточнять по мере описания потоков. Не нужно искусственно сохранять сценарий, если выяснится, что он дублирует другой или не относится к MVP.

## 5. Вопросы, которые следует прояснить сценариями

В первую очередь сценарии должны помочь ответить на следующие продуктовые вопросы:

- Может ли RepoDocs начать работу в директории без Git?
- Обязателен ли Git для инициализации, чтения и изменения данных RepoDocs или только для Git-связанных возможностей?
- Как пользователь выбирает проект и повторно открывает его?
- Что именно означает «подключить существующий проект»?
- Какие операции доступны через CLI, а какие — через Web UI?
- Какие сущности и поля пользователь может изменять в Web UI в MVP?
- Как пользователь ожидает увидеть внешние изменения файлов?
- Что происходит при конфликте изменений и кто принимает решение о разрешении?
- Как соотносятся несколько экземпляров RepoDocs, несколько проектов и несколько worktree?
- Какую роль Git играет в повседневном workflow, а какую — в хранении и распространении данных?

Ответы не следует выводить из текущей архитектуры автоматически. Их необходимо сформулировать как продуктовые ожидания и согласовать.

## 6. Предлагаемая последовательность документации

Предлагается использовать следующую цепочку артефактов:

```text
Product Vision
     |
     v
User Scenarios & Core Workflows
     |
     v
Requirements Specification
     |
     v
Architecture Overview
     |
     v
Technical Specifications
```

Назначение уровней:

| Артефакт | На какой вопрос отвечает |
| --- | --- |
| Product Vision | Зачем существует продукт, для кого он и какие проблемы решает? |
| User Scenarios & Core Workflows | Как пользователь взаимодействует с продуктом и достигает своих целей? |
| Requirements Specification | Какие функциональные требования и ограничения следуют из сценариев? |
| Architecture Overview | Как система на концептуальном уровне реализует требования? |
| Technical Specifications | Каковы конкретные контракты, модели данных, API и механизмы реализации? |

Это предлагаемая структура, а не окончательно утверждённая система документации. В частности, объём и форма Requirements Specification могут быть определены после подготовки первых сценариев. Не следует создавать отдельный документ ради формального соблюдения цепочки, если требования можно зафиксировать компактно и без дублирования.

## 7. Предлагаемый порядок дальнейшей работы

1. Зафиксировать текущую версию Architecture Overview v0.2 и результаты уже проведённого ревью, не продолжая сейчас архитектурную правку.
2. Подготовить и согласовать User Scenarios & Core Workflows.
3. На основе сценариев выделить функциональные требования, ограничения MVP и открытые продуктовые вопросы.
4. Вернуться к Architecture Overview v0.2 и проверить каждое спорное решение на соответствие сценариям и требованиям.
5. Только после этого решать, какие замечания ревью требуют изменения архитектуры, какие относятся к техническим спецификациям, а какие можно закрыть без изменений.

Замечания ревью остаются полезными наблюдениями. Пауза означает не отказ от них, а перенос окончательной оценки до появления недостающего контекста.

## 9. Первый вопрос для проработки

В качестве первого предлагается разобрать сценарий **«Создание нового проекта»**.

Исходная ситуация:

- пользователь хочет начать новый проект;
- у него есть пустая директория;
- Git ещё не инициализирован;
- исходного кода и проектной документации пока нет;
- пользователь запускает RepoDocs.

Ключевой вопрос: какое поведение RepoDocs ожидается в этой ситуации?

Возможные направления для обсуждения:

1. RepoDocs позволяет начать с создания проектного контекста, а Git можно подключить позже.
2. RepoDocs требует предварительно создать Git-репозиторий.
3. RepoDocs поддерживает оба пути и предлагает пользователю выбрать.

Ни один из вариантов пока не принят. Ответ должен быть определён исходя из целевого пользовательского опыта, а не из текущего алгоритма A-08.
